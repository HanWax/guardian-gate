# Security Best Practices Review Report

## Executive Summary
This codebase has multiple authorization design flaws that allow privilege escalation and cross-tenant data access/modification. The highest-risk issues come from trusting user-controlled role claims and using the Supabase service-role key in user-facing server functions without strict tenant scoping. I also found token-handling and database policy gaps that increase exposure.

## Critical Findings

### GG-SEC-001 - Privilege Escalation via User-Controlled Role Claim
- Severity: Critical
- Location:
`src/lib/server/auth.ts:15`
`src/lib/server/auth.ts:18`
`supabase/migrations/20260205000005_add_rls_policies.sql:21`
`supabase/migrations/20260205000005_add_rls_policies.sql:24`
- Evidence:
```ts
// src/lib/server/auth.ts
return { user, role: user.user_metadata?.role as string | undefined }
if (role !== 'admin') throw new Error('אין לך הרשאה לבצע פעולה זו')
```
```sql
-- supabase/migrations/20260205000005_add_rls_policies.sql
(auth.jwt() -> 'user_metadata' ->> 'role')
```
- Impact: Any authenticated user who can alter `user_metadata.role` can become `admin`, bypassing app checks and RLS role logic.
- Fix:
Use server-controlled claims only (`app_metadata`) or authoritative DB role tables keyed by `auth.uid()`.
Never authorize from `user_metadata`.
- Mitigation:
Audit recently issued tokens and role changes; force session refresh/invalidation after role model fix.
- False positive notes:
If role mutation is explicitly blocked in your Supabase auth settings/hooks, confirm and document that control.

### GG-SEC-002 - Cross-Tenant BOLA/IDOR from Service-Role + Missing Nursery Scoping
- Severity: Critical
- Location:
`src/lib/server/auth.ts:5`
`src/lib/server/auth.ts:8`
`src/lib/server/teachers.ts:33`
`src/lib/server/teachers.ts:55`
`src/lib/server/nurseries.ts:47`
`src/lib/server/nurseries.ts:66`
`src/lib/server/children.ts:66`
`src/lib/server/parents.ts:81`
`src/lib/server/attendance.ts:47`
- Evidence:
```ts
// src/lib/server/auth.ts
const supabaseServiceKey = process.env.SUPABASE_SERVICE_ROLE_KEY!
return createClient<Database>(supabaseUrl, supabaseServiceKey)
```
```ts
// Example unscoped operations
.from('nurseries').update(data.settings).eq('id', data.nurseryId)
.from('teachers').update(data.teacher).eq('id', data.id)
```
- Impact: Admins from one nursery can read/update/delete records in other nurseries by UUID or nursery ID.
- Fix:
For user-facing operations, prefer user-scoped Supabase clients (RLS enforced) over service-role.
If service-role must remain, enforce explicit nursery ownership checks before every read/write.
- Mitigation:
Add DB constraints/RPC wrappers that reject cross-nursery mutations by default.
- False positive notes:
This is valid even if UUIDs are hard to guess; IDs are frequently discoverable through logs, exports, or related APIs.

## High Findings

### GG-SEC-003 - Authenticated Users Can Mutate/Read Unrelated Family Data
- Severity: High
- Location:
`src/lib/server/children-parents.ts:45`
`src/lib/server/children-parents.ts:59`
`src/lib/server/children-parents.ts:75`
`src/lib/server/children.ts:32`
`src/lib/server/parents.ts:55`
- Evidence:
```ts
// src/lib/server/children-parents.ts
await requireAuth(data.accessToken)
.insert({ child_id: data.assignment.child_id, parent_id: data.assignment.parent_id })
```
```ts
// src/lib/server/children.ts
await requireAuth(data.accessToken)
.from('children').select('*').eq('id', data.id).single()
```
- Impact: Any authenticated user (including teacher role) can modify child-parent links and fetch arbitrary child/parent records by UUID.
- Fix:
Require role-specific authorization (admin where needed) and validate that referenced entities belong to caller’s nursery.
- Mitigation:
Add immutable audit logs for assignment changes and alerts on cross-nursery IDs.
- False positive notes:
If these endpoints are intentionally teacher-writable, that policy should be explicit and still nursery-scoped.

### GG-SEC-004 - Access Tokens Sent in URL Query for GET Server Functions
- Severity: High
- Location:
`src/lib/server/children.ts:16`
`src/lib/queries/children.ts:27`
`node_modules/@tanstack/start-client-core/dist/esm/client-rpc/serverFnFetcher.js:33`
`node_modules/@tanstack/start-client-core/dist/esm/client-rpc/serverFnFetcher.js:69`
- Evidence:
```ts
// serverFnFetcher.js
if (first.method === "GET") { ... url += `?${encodedPayload}` ... }
payloadToSerialize["data"] = opts.data
```
`opts.data` in this app includes `accessToken`.
- Impact: Bearer tokens can leak via access logs, proxies, tracing systems, and URL capture.
- Fix:
Change auth-bearing server functions to `POST` only.
Prefer HTTP-only session cookies/server session extraction rather than passing access tokens from client payload.
- Mitigation:
Immediately scrub query strings from logs and observability pipelines.
- False positive notes:
Even if browser history does not show these URLs, network and server-side logs still can.

### GG-SEC-005 - New Tables Created Without RLS/Policies
- Severity: High
- Location:
`supabase/migrations/20260211000001_add_morning_message_tracking.sql:5`
`supabase/migrations/20260213000002_create_admins_table.sql:1`
`supabase/migrations/20260205000005_add_rls_policies.sql:8`
- Evidence:
`admins` and `morning_message_runs` are created in later migrations, but there is no subsequent `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` or policies for them.
- Impact: Under typical Supabase defaults, anon/authenticated roles may directly access these tables if grants permit.
- Fix:
Enable RLS and add least-privilege policies for both tables; explicitly review/restrict grants.
- Mitigation:
Run a one-time access test with anon/authenticated keys against both tables in staging and production.
- False positive notes:
If your environment has custom revoked grants, verify and document it; RLS should still be enabled for defense-in-depth.

### GG-SEC-008 - Missing Server-Side Auth Check in `getNurseries`
- Severity: High
- Location:
`src/lib/server/nurseries.ts:30`
`src/lib/server/nurseries.ts:32`
- Evidence:
```ts
export const getNurseries = createServerFn({ method: 'GET' })
  .inputValidator(tokenSchema)
  .handler(async () => {
    const supabase = createServiceClient()
```
`accessToken` is validated for shape but never authenticated (`requireAuth` is not called).
- Impact: Callers with arbitrary token strings can enumerate nursery IDs/names.
- Fix:
Call `requireAuth(data.accessToken)` (and ideally role/tenant checks) before querying.
- Mitigation:
Add endpoint-level tests that verify unauthenticated and invalid-token requests are rejected.
- False positive notes:
If this function is guaranteed to be unreachable externally in your deployment model, document that assumption explicitly.

## Medium Findings

### GG-SEC-006 - Fail-Open Fallback Returns All Parents on Scoped Query Error
- Severity: Medium
- Location:
`src/lib/server/parents.ts:31`
`src/lib/server/parents.ts:33`
- Evidence:
```ts
if (error) {
  const { data: all } = await supabase.from('parents').select('*')
  return all
}
```
- Impact: Any transient scoped-query failure can degrade into full parent directory exposure.
- Fix:
Fail closed: return error instead of broad fallback.
- Mitigation:
Alert on scoped-query failures to avoid silent data-expansion behavior.
- False positive notes:
Still a security defect even if the join failure is rare.

### GG-SEC-007 - PII Logged from Incoming WhatsApp Messages
- Severity: Medium
- Location:
`src/lib/server/whatsapp-webhook.ts:704`
- Evidence:
```ts
console.log('[WhatsApp Message Received]', {
  sender: parsed.sender,
  messageText: parsed.messageText,
  ...
});
```
- Impact: Sensitive phone numbers and message content may persist in logs beyond intended retention/access controls.
- Fix:
Redact or hash identifiers, avoid logging raw message bodies, and enforce structured log privacy policy.
- Mitigation:
Restrict log access and retention windows for existing collected data.
- False positive notes:
If logs are strictly isolated and encrypted, risk is reduced but still present for insider/misconfiguration scenarios.

## Verification Gaps and Assumptions
- I could not run vulnerability advisory checks (`npm audit`) because network access to npm registry was unavailable in this environment.
- Security headers/CSP appear absent in app code; these may be enforced at edge/CDN and should be runtime-verified.
